## Remaining operator verification

The runner test does not validate the real VPS's firewall/kernel capabilities, UID permissions, actual port availability, DNS, public Let's Encrypt certificate, Nginx vhost conflicts, timers after reboot, or off-host storage of recovery keys/backups. The Persian guide contains commands for these checks. Per-UID firewall command construction is tested using mocks; actual egress blocking must be verified on the target before staging is accepted. Never disable the required egress unit to work around a startup failure.

## Files and responsibilities

- `server/environment.ts`: APP_ENV identification, path/resource guards, environment marker, outbound policy, staging-only runtime HTML.
- `server/database.ts`, `server/session-config.ts`: persistent identity and independent session namespace.
- `server/notifications.ts`, `server/translator.ts`, `server/media.ts`, `server/backups.ts`: suppress external providers and protect resource boundaries.
- `server/dev.ts`, `server/api.ts`, `api/app.ts`, `src/App.tsx`, `src/index.css`: runtime identity, localhost binding, indexing restrictions and staging indicator; production branding retained.
- Database/backup/provider/rollback CLI entry points validate staging targets before opening resources. The production deployment helper refuses a staging context.
- `ops/staging/`: separate environment/secret generation, Nginx HTTP bootstrap and HTTPS Basic Auth, systemd web/egress/backup units and timer, UID firewall, certificate renewal hook and log rotation.
- `server/environment.test.ts`, `scripts/staging-smoke.mjs`, `.github/workflows/staging-isolation.yml`, `package.json`: isolation regression tests and disposable CI integration.
- `.env.example`, `STAGING_SETUP_FA.md`: compatibility notes and complete Persian installation, update, verification, troubleshooting and rollback guidance.
