# پایگاه دادهٔ رابطه‌ای YEREVANHUB، نسخهٔ ۳

## تصمیم معماری

این نسخه روی همان libSQL/SQLite فعلی اجرا می‌شود؛ تغییر DATABASE_URL، خرید سرویس جدید، نصب PostgreSQL یا انتقال فایل‌های عکس لازم نیست. ساختار یکپارچهٔ JSON از مسیر فعال حذف شده است. جدول‌های SQL و ایندکس‌ها مرجع اطلاعات هستند. مدل TypeScript و قرارداد API فعلی برای جلوگیری از شکستن پنل‌ها حفظ شده‌اند.

JSON فقط برای داده‌های انعطاف‌پذیر مثل امکانات و قوانین ملک، قواعد قیمت و تصویر ثابت توافق رزرو باقی مانده است. شناسه‌ها، ارتباط‌ها، وضعیت‌ها، تاریخ اقامت، تعداد واحد، مبلغ، حساب‌ها و محتوای مقاله ستون‌های مستقل دارند. `extras_json` نیز فیلدهای اختیاری/قدیمی را برای مهاجرت بدون حذف اطلاعات نگه می‌دارد؛ این ستون جایگزین جدول رزرو یا کاربران نیست.

## نقشهٔ جدول‌ها

| گروه | جدول‌ها | ارتباط اصلی |
|---|---|---|
| حساب | `users`, `user_credentials`, `manager_properties` | رمز به کاربر؛ مدیر به هاستل |
| اقامتگاه | `properties`, `property_translations` | کلید ترکیبی نوع و شناسه؛ متن‌های چهارزبانه |
| اتاق و موجودی | `room_types`, `room_translations`, `physical_units`, `capacity_overrides` | نوع اتاق به هاستل؛ تخت یا اتاق واقعی به نوع اتاق |
| تصاویر | `property_photos`, `property_images`, جدول موجود `media_assets` | عکس به ملک؛ فایل در فضای ذخیره‌سازی فعلی |
| رزرو | `bookings`, `booking_units`, `booking_events` | رزرو به هاستل و نوع اتاق؛ تخصیص به واحد فیزیکی |
| تعمیرات | `unit_blocks`, `unit_block_units` | مسدودسازی به واحدهای واقعی همان اتاق |
| اجاره | `rental_inquiries` | درخواست به خانهٔ مربوط |
| محتوا | `articles`, `article_translations`, `reviews`, `phrases` | نظر به هاستل و رزرو؛ ترجمه به مقاله |
| عملیات | `booking_changes`, `support_threads`, `support_messages`, `finance_entries` | تغییر، پیام و ثبت مالی به رزرو |
| عمومی | `coupons`, `saved_places`, `audit_logs`, `app_settings` | علاقه‌مندی به حساب؛ تنظیمات به کلید |
| زیرساخت | `sessions`, `auth_tokens`, `rate_limits`, `outbox`, `schema_migrations`, `migration_backups` | نشست، توکن، محدودسازی و صف ارسال فعلی |

کلیدهای خارجی از ثبت رزرو برای اتاق ناموجود و تخصیص تخت متعلق به اتاق دیگر جلوگیری می‌کنند. آدرس ایمیل بدون حساسیت به حروف و کلید تکرار درخواست رزرو یکتا هستند. کلید تکرار درخواست باعث می‌شود دوبار لمس‌کردن دکمهٔ ثبت، دو رزرو نسازد. قیمت و شرایط پذیرفته‌شده در `agreement` حفظ می‌شوند.

نمونه‌های قدیمی ممکن است نظرهایی با شناسهٔ رزرو ناموجود داشته باشند. در مهاجرت، همان شناسه در `legacy_booking_id` حفظ می‌شود؛ رزرو یا مسافر ساختگی ایجاد نمی‌شود. نظر جدید باید رزرو معتبر داشته باشد.

SQL کامل در [DATABASE_SCHEMA_V3.sql](DATABASE_SCHEMA_V3.sql) و تعریف مرجع در `server/relational-schema.ts` قرار دارد. فایل SQL صرفاً نقشهٔ ساختار است؛ برای انتقال اطلاعات فعلی، فرمان مهاجرت را اجرا کنید.

## چرا پردازش و نوشتن کمتر می‌شود؟

- بازدید عمومی یک تراکنش خواندنی است؛ به‌خاطر دیدن صفحه، داده‌های سایت دوباره نوشته نمی‌شوند.
- دسترسی به فایل عکس یا صف اعلان‌ها، کاربران و رزروهای سایت را بارگذاری نمی‌کند.
- محاسبهٔ ظرفیت ۹۱ روزه با جست‌وجوی SQL ایندکس‌شده انجام می‌شود و برای بازدید عمومی، نام و تماس مسافران و رزروهای تاریخی خوانده نمی‌شوند.
- درخواست رزرو، اطلاعات همان هاستل و رزروهای لازم برای کنترل موجودی را می‌خواند.
- جست‌وجوی موجودی از تاریخ خروج استفاده می‌کند تا رزروهای پایان‌یافته کنار گذاشته شوند؛ رزروهای فعال و مهمانانی که هنوز خارج نشده‌اند نیز مسیرهای ایندکس‌شدهٔ مستقل دارند.
- تغییر یک مشخصهٔ ملک، سطر همان ملک را به‌روز می‌کند؛ اتاق‌ها، عکس‌ها و سایر اقامتگاه‌ها بی‌دلیل بازنویسی نمی‌شوند.
- فیلترهای هر درخواست در `server/repository.ts` تعریف شده‌اند. داده‌ای که بارگذاری نشده هرگز به دلیل نبودن در حافظه حذف نمی‌شود.
- ایندکس‌ها برای ظرفیت، رزروهای کاربر، وضعیت/مهلت رزرو، صف ارسال، انقضای نشست و مرتب‌سازی وجود دارند.
- حسابرسی به ۵۰۰ مورد اخیر محدود می‌ماند؛ نشست‌ها، شمارنده‌ها و توکن‌های منقضی در Worker پاک‌سازی می‌شوند.
- برای فایل محلی SQLite، WAL فعال است تا خواندن هم‌زمان با نوشتن بهتر انجام شود.

محدودیت: API فعلی هنوز فهرست کامل اقامتگاه‌های منتشرشده را به مرورگر می‌دهد و پنل مدیر برای سازگاری، نمای کامل داده‌های مدیریتی را دریافت می‌کند. برای هزاران آگهی یا تاریخچهٔ بسیار بزرگ، گام بعدی صفحه‌بندی API/پنل و بارگذاری جزئیات به درخواست است. این نسخه ادعای ظرفیت نامحدود یا حذف همهٔ هزینه‌ها ندارد. قرارداد صفحه‌بندی نیازمند تغییر هم‌زمان رابط کاربری است.

## مهاجرت چه چیزهایی را حفظ می‌کند؟

شناسهٔ کاربران، هش و نمک رمز، نشست‌ها، توکن‌ها، نشانی عکس‌ها و فایل‌های آن‌ها، اقامتگاه‌ها، رزروها، توافق قیمت، وضعیت‌ها، درخواست‌های خانه، نظرها، مقاله‌ها و ترجمه‌ها، کدهای تخفیف، تخصیص تخت و سوابق عملیاتی حفظ می‌شوند. برنامه در مهاجرت حساب مدیر تازه را جایگزین مدیر موجود نمی‌کند.

تبدیل در یک تراکنش انجام می‌شود. خروجی دوباره به مدل برنامه برگردانده و با اصل داده مقایسه می‌شود. اگر دادهٔ ناسازگار، شناسهٔ تکراری یا نقض رابطه وجود داشته باشد، نسخهٔ ۳ ثبت نمی‌شود و تغییرات همان مهاجرت برمی‌گردند. جدول‌های قدیمی با نام‌های `legacy_app_state_v2`, `legacy_properties_v2`, `legacy_operational_records_v2` به‌عنوان نسخهٔ بازیابی نگه داشته می‌شوند و در درخواست‌های عادی استفاده نمی‌شوند. این‌ها نسخهٔ زمان مهاجرت‌اند؛ برای بازیابی آخرین ویرایش‌ها از فرمان rollback استفاده کنید.

## اعمال روی VPS فعلی

پیش از تغییر، خروجی‌های زیر را نگه دارید؛ هیچ رمز یا محتوای `.env` را ارسال نکنید:

```bash
sudo -u hostel2 git -C /opt/hostel2/app rev-parse HEAD
sudo systemctl list-units --type=service --all 'hostel2*' --no-pager
```

این راهنما فرض می‌کند سرویس وب `hostel2` و در صورت وجود سرویس Worker، نام آن `hostel2-worker` است. اگر Worker با cron یا نام دیگری اجرا می‌شود، همان را هم تا پایان مهاجرت متوقف کنید.

۱. برای این ارتقا یک توقف کوتاه در نظر بگیرید. وب و تمام Workerها/زمان‌بندها را پیش از دریافت کد متوقف کنید؛ شروع هر پردازش با کد جدید می‌تواند مهاجرت خودکار را اجرا کند:

```bash
sudo systemctl stop hostel2
# فقط اگر این سرویس را دارید:
# sudo systemctl stop hostel2-worker
```

۲. کد جدید را دریافت و ساخت آن را کامل کنید. فایل دیتابیس و پوشهٔ عکس‌ها را جابه‌جا یا حذف نکنید:

```bash
sudo -u hostel2 -H bash <<'SH'
set -e
export PATH="/opt/hostel2/node/bin:$PATH"
cd /opt/hostel2/app
git pull --ff-only origin codex/public-property-preview
npm run lint
npm run build
SH
```

۳. یک پشتیبان کامل رمزنگاری‌شده با فرمان موجود پروژه تهیه کنید. `BACKUP_ENCRYPTION_KEY` باید قبلاً در محیط محافظت‌شده/فایل `.env` تنظیم شده باشد. کلید را در خروجی یا پیام‌ها ننویسید؛ بدون همان کلید فایل پشتیبان قابل بازیابی نیست:

```bash
sudo -u hostel2 -H bash <<'SH'
set -e
export PATH="/opt/hostel2/node/bin:$PATH"
cd /opt/hostel2/app
npm run backup
npm run db:migrate
npm run db:check
SH
```

اگر فرمانی خطا داد، سرویس را با نسخهٔ جدید شروع نکنید؛ خروجی خطای بدون اطلاعات محرمانه را بررسی کنید. نسخهٔ پشتیبان را به فضای محافظت‌شدهٔ دیگری کپی کنید. نسخهٔ داخلی مهاجرت جای پشتیبان کامل جدا از سرور را نمی‌گیرد.

۴. وقتی `db:check` بدون خطا تمام شد، باید نسخهٔ ۳، `schemaReady: true`، صفر نقض کلید خارجی و نتیجهٔ `integrity_check: ok` را ببینید. سپس سرویس‌ها را شروع کنید:

```bash
sudo systemctl start hostel2
# در صورت وجود:
# sudo systemctl start hostel2-worker
sudo systemctl status hostel2 --no-pager
```

Worker را با تنظیمات فعلی پروژه فعال نگه دارید. انقضای رزروها و ارسال اعلان‌ها دیگر به بازدید از صفحهٔ عمومی وابسته نیست. اگر Worker مستقل ندارید، راه‌اندازی آن را مطابق بخش Worker در README انجام دهید؛ چند اجرای هم‌زمان غیرضروری ایجاد نکنید.

## بازگشت به نسخهٔ قبلی بدون دورریختن ویرایش‌های جدید

وب و تمام Workerها را متوقف کنید و پشتیبان کامل تازه بگیرید. سپس، با کد نسخهٔ ۳ که هنوز روی دیسک است:

```bash
sudo -u hostel2 -H bash <<'SH'
set -e
export PATH="/opt/hostel2/node/bin:$PATH"
cd /opt/hostel2/app
npm run db:rollback -- --offline
SH
```

این فرمان از **داده‌های فعلی** جدول‌های رابطه‌ای، ساختار نسخهٔ ۲ را دوباره می‌سازد؛ صرفاً snapshot قدیمی را برنمی‌گرداند. بعد از موفقیت، کد را به commit پیش از ارتقا که در مرحلهٔ اول یادداشت کردید برگردانید و build کنید، سپس سرویس‌ها را شروع کنید. اجرای دوبارهٔ کد نسخهٔ ۳، مهاجرت رو به جلو را دوباره انجام خواهد داد.

برای بازیابی از فایل پشتیبان نیز فرمان موجود `npm run restore -- <file.yhbak>` باید به یک دیتابیس و پوشهٔ عکس خالی و جداگانه هدایت شود؛ پایگاه دادهٔ زنده را overwrite نمی‌کند. پشتیبان نسخهٔ جدید اکنون ایندکس‌ها را نیز نگه می‌دارد و جدول‌های والد را پیش از داده‌های فرزند می‌سازد.

## بررسی‌ها

`npm test` شامل آزمون‌های مهاجرت بدون حذف داده، برگشت و مهاجرت مجدد، شکست اتمیک دادهٔ ناسازگار، حفظ رمز و عکس، جلوگیری از تأیید هم‌زمان آخرین ظرفیت، یکتایی درخواست، محدودیت دسترسی، بازیابی پشتیبان و کنترل حجم نوشتن است. آزمون عملکرد ساختاری تأیید می‌کند تغییر تلفن یک ملک یک سطر را می‌نویسد و بازدید عمومی هیچ دادهٔ برنامه‌ای را نمی‌نویسد؛ این ادعای زمان پاسخ تضمین‌شده روی سرور واقعی نیست.
